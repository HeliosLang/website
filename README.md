# Helios website and debugger operations

The Docusaurus site builds into `dist`. The `/console/debugger` page manages wallet-authenticated debugger API keys. Captures and replay belong to the original `tx-utils`, `contract-utils`, ledger and VS Code repositories. Cloudflare Worker + D1 + private R2 replace the milestone's proposed AWS infrastructure.

## Local development

Use Node 24.11.0 and pnpm 10.20.0:

```sh
pnpm install --frozen-lockfile
pnpm start
pnpm typecheck
pnpm build
```

The Worker lives in this repository at `services/debugger`:

```sh
cd services/debugger
pnpm install --frozen-lockfile
pnpm exec wrangler d1 migrations apply DB --local
pnpm dev
pnpm test
pnpm check
```

For local console development, start Docusaurus with `DEBUGGER_API_URL=http://localhost:8787`. The Worker allows exactly `http://localhost:3000` locally. Wallet globals are accessed only in browser event handlers inside `BrowserOnly`. Production cookies are Secure, HttpOnly and SameSite=Strict; local wallet integration may require HTTPS depending on the browser. Verify deployed wallet sessions on the production console.

## Deployment architecture

`.github/workflows/build.yml` checks pull requests without production credentials. Pushes to `main` and manual dispatch on `main` deploy production. There is one hosted environment, using one production Pages project. Deployments are serialized without cancellation. Checks/builds run in a separate job before credentials become available. Only provisioning and Wrangler deployment steps receive the Cloudflare token.

The Worker source, migrations, tests and locked service dependencies live in `services/debugger`. CI checks and deploys the backend and frontend from the same website commit. No separate backend manifest, download or npm release is needed. Website-only test helpers live beside the service tests; the service has no dependency on `tx-utils`.

Keep backend changes backward-compatible with the currently deployed frontend: migrations run before Worker deployment, and a failed health check prevents the Pages upload. Destructive migrations need a separate staged migration plan.

`deployment/production.json` defines non-secret Pages/Worker/D1/R2 names, exact website origin and Worker hostname. Provisioning reuses the Pages project named `helioslangplatform` in `deployment/production.json`, or creates it with production branch `main` when missing. It also discovers existing named D1/R2 resources, creates missing ones, enables a 30-day R2 lifecycle, and writes an ephemeral Wrangler config. SQL migrations are repeatable via D1's migration ledger. The Worker publishes capture indices only after R2 storage succeeds and removes expired index records hourly. Payloads are limited to 10 MiB. D1 counters enforce per-IP and per-key rate limits.

An existing Pages project keeps its configuration and domain. A newly created project uses Direct Upload with `main` as its production branch. Attach the production custom domain and configure its DNS in Cloudflare for a new project before the final console smoke check can pass; the workflow does not change website DNS. Existing projects must also use `main` as their production branch. If Git integration is enabled, disable automatic production and preview Git builds in that project's Settings → Builds & deployments → Branch control. Do not delete/recreate the project. Cloudflare supports Wrangler uploads into Git-integrated projects: [Git integration documentation](https://developers.cloudflare.com/pages/configuration/git-integration/).

## Cloudflare API token and GitHub configuration

A **Cloudflare API token** deploys infrastructure. It is entirely different from the **debugger API keys** generated by the wallet console. Never put either into Docusaurus public configuration, source files or generated assets.

1. Open Cloudflare Dashboard → My Profile → API Tokens (or account API tokens) → Create Token → Custom token → Get started.
2. Name it `Helios GitHub deployment`.
3. Add these account-scoped permissions, restricted to the account where the platform will be deployed:
   - Cloudflare Pages — Edit
   - Workers Scripts — Edit
   - D1 — Edit
   - Workers R2 Storage — Edit
4. Add Zone → Workers Routes — Edit, restricted to `helios-lang.io`, for the Worker's custom domain. If your account requires zone discovery for Wrangler, also grant Zone → Zone — Read on this same zone.
5. Set a suitable expiry, review the summary, create the token and copy it once.
6. In the website GitHub repository, use the `cloudflare` environment. Add secret `CLOUDFLARE_API_TOKEN` and variable `CLOUDFLARE_ACCOUNT_ID`. The Pages project name is committed in `deployment/production.json`; no GitHub project-name variable is needed. Store the account ID as a variable, as the workflow reads it through `vars`.
7. Verify `deployment/production.json` against the chosen account, domains and resource names. R2 buckets must remain private; do not enable public access.

Cloudflare is migrating the legacy Edit permission names above to roles. If the dashboard shows the newer selector, use Workers product-level Admin for first Worker creation (Editor is sufficient for later updates), Pages Write, and Zone → Workers Routes → Write on the same zone, plus the D1 and R2 resource permissions. Existing legacy permissions remain supported; consult the current role mapping linked below.

Official references: [CI token creation](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/), [permission names](https://developers.cloudflare.com/fundamentals/api/reference/permissions/), [custom-domain permissions](https://developers.cloudflare.com/workers/authorization/workers/).

## First deployment

1. Run frontend checks and the tests in `services/debugger`. Review the Worker and website changes together.
2. Configure the `cloudflare` GitHub environment above before merging the workflow to `main`. Disable overlapping Cloudflare Git builds if enabled.
3. Merge the website changes into `main` to trigger deployment. Later deployments can also be started manually on `main`, without environment inputs. Inspect provisioning, migrations, Worker health checks and the Pages upload.
4. Confirm `https://debugger.helios-lang.io/v1/health` returns `{"ok":true,"apiVersion":1}`; unauthenticated `/v1/captures` must return 401. Visit `https://helios-lang.io/console/debugger`, connect a wallet, create two keys, upload a capture with one and verify the other cannot read it. Revoke a key and confirm its feed returns 401.
5. Inspect the production smoke checks and deployment summary containing the website commit covering both frontend and backend. A subsequent manual deployment can verify resource discovery and migration idempotency. A failed backend check prevents Pages deployment.

Builds do not receive deployment credentials. The only public endpoint setting is `DEBUGGER_API_URL`. Inspect `dist` before release for secret-like content; never test secret exclusion by supplying a real token to the build.

## Rotation and rollback

Create a replacement Cloudflare token with the same limited permissions, update the GitHub environment secret, manually deploy production and verify its health, then revoke the old token. Rotate debugger keys independently in the console; configure the new key in CLI profiles/VS Code before revoking the previous key.

For a frontend rollback, redeploy a known-good website commit, which includes its backend implementation, or use Pages' deployment rollback. For a Worker rollback, use `pnpm exec wrangler rollback <VERSION_ID> --config wrangler.deploy.json` with the matching environment configuration. D1 migrations are not automatically rolled back. Preserve compatible schema and R2 data; use a forward corrective migration if needed. Always repeat health and console checks after rollback.
